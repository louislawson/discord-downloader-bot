# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Discord bot that streams every allowed-MIME attachment in a channel into one zip and delivers it via a SAS-signed Azure Blob Storage URL (default TTL 24h, per-guild configurable). The pipeline is end-to-end streaming (`channel.history()` → aiohttp chunked GET → `stream-zip` → Azure block-blob upload), so worker memory stays bounded regardless of channel size. The bot only enqueues Taskiq tasks — a Taskiq worker (separate compose service, same image) pulls them off RabbitMQ and runs the channel-history walk, zip, upload, and delivery, so the work outlives the 15-minute Discord interaction-token window and parallel `/download`s in different channels don't block each other. Python 3.12, discord.py 2.6.4, taskiq 0.12.3 (`taskiq-aio-pika` 0.6.0 broker, `taskiq-redis` 1.2.2 result backend, `taskiq-cancellation` 0.0.1, `taskiq-dependencies` 1.5.7), azure-storage-blob 12.28.0, asyncpg 0.30.0, stream-zip ≥0.0.83, pydantic-settings 2.14.0.

## Common commands

Dev — auto-reloads on any `.py` change under `downloader_bot/` (bot watches via `watchfiles`; worker/scheduler watch via Taskiq's `--reload` flag):

```bash
cp .env.example .env   # fill in TOKEN + RABBITMQ_DEFAULT_USER/PASS; for Azurite see README quickstart
docker compose up      # bot + worker + scheduler + rabbitmq + redis + postgres + azurite + taskiq_admin
```

Production:

```bash
docker build -t downloader-bot:<VERSION> .
docker run -d --name downloader-bot --env-file .env.prod downloader-bot:<VERSION>
```

ARM64 (e.g. Raspberry Pi): `docker build --platform linux/arm64/v8 -t downloader-bot:<VERSION>-arm64-v8 .`

Tests / lint / format are wired through a `Makefile` (pytest, ruff, pre-commit; configured in `pyproject.toml` and `.pre-commit-config.yaml`):

```bash
make install-dev    # installs requirements-dev.txt + runs `pre-commit install`
make test           # python -m pytest
make test-cov       # pytest with coverage; HTML report at htmlcov/index.html
make lint           # ruff check (no edits)
make format         # ruff format + ruff check --fix in place
make check          # lint + format-check + test — the pre-push gate
```

Tests are unit-only with mocks for Discord, Azure, asyncpg, Redis, and Taskiq context — **no compose stack is required to run them**. There is no CI yet, so `make check` is the only gate before merging.

## Architecture

### Three processes, one image

The same Docker image runs as three compose services with different `CMD`s:

- **bot** — connects to the Discord gateway, exposes slash/prefix commands, opens an asyncpg pool to Postgres. Commands enqueue Taskiq tasks via `download_channel_media.kiq(...)` and ack the user; they don't do work. `setup_hook` calls `broker.startup()` (skipped on the worker side via `broker.is_worker_process`) so the bot can publish to RabbitMQ.
- **worker** — `python -m taskiq worker downloader_bot.tq:broker downloader_bot.tasks`. REST-only Discord client (no gateway), asyncpg pool, dedicated `aiohttp.ClientSession` for CDN streams, storage backend kept warm in an `AsyncExitStack`, and a separate Redis client for app-namespaced idempotency state. Multiple workers can run in parallel; per-channel ordering isn't guaranteed.
- **scheduler** — `python -m taskiq scheduler downloader_bot.tq:scheduler downloader_bot.tasks`. Reads cron-style schedules from the Redis schedule source + Taskiq label decorators. No scheduled tasks are wired up today; the service is kept running so the cron surface is available the moment a `@broker.task(schedule=[...])` is added.

The split exists because zipping a busy channel routinely takes longer than Discord's 15-minute interaction-token window. Decoupling also lets independent channels run in parallel.

### Entry point

`downloader_bot/bot.py` defines `DiscordBot(commands.Bot)`. `setup_hook` runs in this order: log identity → if not `broker.is_worker_process`, call `await broker.startup()` (opens the AMQP connection so `.kiq(...)` can publish) → `build_pool()` (opens the asyncpg pool **and** applies `schema.sql` idempotently) → construct `GuildSettingsRepo(db_pool)` on `self.guild_settings_repo` for `/setup` to read off `self.bot` → `load_cogs()` (scans `downloader_bot/cogs/`, skips `_`-prefixed files, dynamically `load_extension()`s every `.py` file as `downloader_bot.cogs.<name>`) → start `discordhealthcheck` server → start `status_task`. Adding a cog = drop a file in `downloader_bot/cogs/` with an `async def setup(bot)` — no registration list to update. `close()` mirrors `setup_hook`: it waits on the healthcheck server, calls `broker.shutdown()` for the non-worker side, calls `close_pool(self.db_pool)`, and then `super().close()`. The worker process opens its own pool inside the `WORKER_STARTUP` hook in `downloader_bot/tq.py` — `CREATE TABLE IF NOT EXISTS` is idempotent, so bot and worker concurrently running `build_pool()` is safe.

`status_task` is a 1-minute `discord.ext.tasks` loop that cycles the bot's "Playing X" presence using `cycle_random(STATUSES)` from `downloader_bot/presence.py`. The picker guarantees the same line never appears twice in a row (relaxed only when the sequence has a single entry). New status strings: edit the `STATUSES` tuple in `downloader_bot/presence.py` — no other wiring needed.

### Cogs

- `downloader_bot/cogs/download.py` — `@commands.hybrid_command` `/download [dm_me] [media_type] [from_user] [before] [after] [during]`. `context.defer(ephemeral=dm_me)` first; pre-checks `Read Message History` for the bot in the channel; rejects conflicting filters (`during` plus `before`/`after`) and parses the relative-duration strings via `downloader_bot/download/filters.py` (`FilterParseError` → red "Invalid filter" embed); then a per-guild rate-limit check via `downloader_bot/download/ratelimit.py` (skipped when `context.guild is None` or when the invoker is `context.guild.owner_id` — guild owners bypass); then calls `await download_channel_media.kiq(channel_id=..., user_id=..., guild_id=..., dm_me=..., filters=...)` (Taskiq returns an `AsyncTaskiqTask[DownloadResult]` whose `.task_id` is included in the queued-ack embed). A rate-limit denial sends a red "Rate limit reached" embed with a live `discord.utils.format_dt(..., 'R')` retry-after, always `ephemeral=True` regardless of `dm_me` (so the throttle reply doesn't itself spam the channel). Any exception from `.kiq(...)` is treated as "RabbitMQ went away after startup" and surfaces the same red "Service unavailable" embed.
- `downloader_bot/cogs/setup.py` — `@commands.hybrid_group` `/setup` with three subcommands: `set` / `show` / `clear`. Server-owner-gated via a custom `_is_guild_owner` predicate on the group (raises `NotGuildOwner(commands.CheckFailure)`) plus `@commands.guild_only()`; both decorators are inherited by every subcommand. Cog-local `cog_command_error` handles `NotGuildOwner` and `NoPrivateMessage` so they don't leak to the global handler. The parent `setup_group` callback emits a `set | show | clear` usage embed for prefix-mode invocations without a subcommand (slash-mode users autocomplete past it).
  - `set <delivery_mode> [results_channel] [retention_hours]` validates `delivery_mode in {dm, channel}` and rejects `channel` mode without a `results_channel` (the schema CHECK constraint would surface as an opaque "Unexpected error" otherwise) before calling `self.bot.guild_settings_repo.upsert(GuildSettings(...))` — a single-shot overwrite, not read-modify-write. `allowed_media_types` and `max_archive_size_bytes` are left at their defaults until separate commands exist for them, so any value previously persisted in those columns will be wiped on `/setup set`.
  - `show` calls `guild_settings_repo.get()` (which returns `GuildSettings(guild_id=N)` defaults for unconfigured guilds — never `None`) and renders an `info` embed with mode / channel / retention. Read-only.
  - `clear` does a read-then-`dataclasses.replace` to flip `delivery_mode` to `dm` and null `results_channel_id` while preserving `retention_hours`, `allowed_media_types`, and `max_archive_size_bytes` — so `clear` can't be used as a backdoor to wipe columns the cog otherwise doesn't expose. Auto-flipping mode also sidesteps the `guild_settings_channel_requires_id` CHECK constraint that would fire if `results_channel_id` were nulled while mode was still `channel`.
- `downloader_bot/cogs/owner.py` — owner-only, prefix-only commands. `<PREFIX>sync global|guild` re-registers slash commands (run this after adding or changing a hybrid command before the slash UI updates). There is no longer a `queueping` smoke-test command — to verify the bot ↔ worker round trip, run `/download` against a small channel.
- `downloader_bot/cogs/general.py` — `@commands.hybrid_command` `/invite`. Sends the bot's invite link via DM, falls back to an ephemeral channel reply if DMs are blocked.

### Broker wiring (`downloader_bot/tq.py`)

The single source of truth for queue infrastructure. Defines:

- **`broker`** — `AioPikaBroker` (RabbitMQ) with `RedisAsyncResultBackend` (24h result TTL, `keep_results=False`). Middlewares: `TaskiqAdminMiddleware` (publishes task lifecycle to the `taskiq_admin` UI), `HeartbeatMiddleware` (heartbeat Redis sentinel for the docker healthcheck — see below), `SimpleRetryMiddleware(default_retry_count=3)`. `task_id` is preserved across retries by `SimpleRetryMiddleware`, which is what the idempotency layer relies on.
- **`cancellation_backend`** — `ModularCancellationBackend` over the same Redis (state holder) + AMQP (notifier). Tasks opt into cancellation by stacking `@cancellation_backend.cancellable` under `@broker.task(...)`.
- **`scheduler`** — `TaskiqScheduler` reading both a `RedisScheduleSource` (dynamic CRUD via the admin UI) and a `LabelScheduleSource(broker)` (static schedules on the `@broker.task(schedule=[...])` decorator).
- **Worker startup/shutdown hooks** (`TaskiqEvents.WORKER_STARTUP` / `WORKER_SHUTDOWN`) — open and tear down shared resources on `state` (the Taskiq per-worker state holder): `discord_client` (REST-only via `open_client`), `download_session` (`aiohttp.ClientSession` used by `zip_stream`, separate from discord.py's HTTPClient so we get direct `iter_chunked` access), `exit_stack` (`AsyncExitStack` that keeps the storage backend's `async with` open for the worker's lifetime so the Azure SDK's connection pool stays warm), `storage` (the entered backend), `db_pool` + `guild_settings_repo`, and `redis` (app-namespaced Redis client for idempotency, distinct from the result-backend Redis).
- **Typed dependency providers** — `get_discord_client`, `get_download_session`, `get_storage`, `get_guild_settings_repo`, `get_redis`. Tasks declare what they need via `Annotated[T, TaskiqDepends(provider)]` parameters. This is the idiomatic Taskiq replacement for ARQ's `ctx['key']` dictionary — typecheckers see real types and unit tests pass mocks as plain function arguments.

### Tasks (`downloader_bot/tasks/`)

- `downloader_bot/tasks/__init__.py` — re-exports `download_channel_media` so the worker's `-tp` path (or implicit module-level import) registers the task.
- `downloader_bot/tasks/download.py` — `download_channel_media(channel_id, user_id, guild_id, dm_me, *, filters=None, ...)` is the public Taskiq task. Decorated with `@broker.task(task_name="download_channel_media", retry_on_error=True, max_retries=3)` then `@cancellation_backend.cancellable`. Return type is a real `TypedDict` (`DownloadResult` — `url`, `delivery_mode`) so callers awaiting the result get a typed payload. The orchestration is two phases, each guarded by an idempotency check so a retry skips already-completed work:
  1. **Upload phase.** If `idempotency.get_cached_archive_url(redis, task_id)` returns a URL, skip the whole upload. Otherwise: `client.fetch_channel(channel_id)` → enforce `discord.abc.Messageable` → build `_display_filename(channel)` (e.g. `channel-general-2026-05-09.zip` — non-ASCII / shell-grief chars are stripped) → call `filters_module.resolve(filters, guild_settings, now=...)` to compose the per-attachment matcher (intersection of category + guild policy + author) and resolve any `before` / `after` / `during` to UTC datetimes → call `zip_stream.build_zip_stream(...)` with the matcher and date bounds → `storage.upload_and_sign(name=key, data=stream, download_filename=...)`. A `try/finally` flips `upload_succeeded`; on any failure path (including `CancelledError`) the partial blob is best-effort `delete_blob(key)`-ed and only documented `UploadError`s are logged-and-swallowed. After the URL is provably good, `idempotency.cache_archive_url(redis, task_id, url, ttl_seconds)` marks the phase complete.
  2. **Deliver phase.** Skip if `idempotency.is_delivered(redis, task_id)`. Otherwise: if `effective_delivery_mode == "channel"` and `results_channel_id` is set, `deliver.post_to_channel(...)` (which itself falls back to DM if the channel is unusable). Otherwise `deliver.dm_user(...)`. Then `idempotency.mark_delivered(redis, task_id, ttl_seconds)` — set **after** the send returns, because a duplicate DM beats no DM.

  Effective delivery mode: `dm_me=True` forces DM. Otherwise `guild_id is not None` triggers a `settings_repo.get(guild_id)` lookup; missing guilds get defaults (`delivery_mode='dm'`, `retention_hours=24`, no media-type filter). The `ttl` passed to the storage backend comes from `guild_settings.retention_hours`. `ProgressTracker` updates are emitted at the `stream` / `deliver` / `done` boundaries for the admin UI.

### Download primitives (`downloader_bot/download/`)

- `downloader_bot/download/zip_stream.py` — `build_zip_stream(session, channel, *, matches=None, before=None, after=None, chunk_size)` returns an `AsyncIterable[bytes]` ready to be fed to the storage backend's `upload_and_sign`. `matches` is a `Callable[[discord.Attachment, discord.Message], bool] | None`; `None` accepts every attachment. `before` / `after` are forwarded to `channel.history(before=, after=)` for free server-side date pruning. `_members` pre-flights each attachment GET; non-200 / setup errors are skipped silently with a warning and **no member tuple** is emitted (so no orphan zip entry). `_stream_response` is the per-attachment bytes generator — `aiohttp.ClientError` mid-body raises `AttachmentStreamError` (the zip is corrupt at that point and the job must abort); the `finally` always calls `resp.release()` so the connection returns to the pool even if the consumer stops early.
- `downloader_bot/download/filters.py` — Per-invocation `/download` filters. `DownloadFilters` `TypedDict` (JSON-friendly payload: `category`, `from_user_id`, `before`, `after`, `during`); `FilterParseError(ValueError)` for cog-side validation. `parse_duration(s)` accepts `Nm`/`Nh`/`Nd`/`Nw` only. `resolve_named_period(name, now)` maps a `Literal` like `last-week` to `(after, before)` UTC datetimes. `CATEGORY_PREDICATES` splits MIME into `image` (non-gif), `video`, `audio`, `gif`, `other`. `resolve(filters, guild_settings, *, now) -> ResolvedFilters` is the single seam the task calls — it composes the per-attachment matcher (category ∩ guild `allowed_media_types` + author) and resolves the date bounds. The cog enforces "`during` mutually exclusive with `before`/`after`" before enqueueing.
- `downloader_bot/download/deliver.py` — `dm_user(client, user_id, archive_url)` and `post_to_channel(client, channel_id, archive_url, *, fallback_user_id)`. DM failures raise `DMUnavailable`. Channel posts fall back to `dm_user(fallback_user_id, ...)` on `NotFound` / `Forbidden` / non-`Messageable`. The orchestrator owns the high-level decision ("DM or channel?"); these helpers own the send.
- `downloader_bot/download/idempotency.py` — Redis-backed phase guards keyed `task:{task_id}:archive_url` and `task:{task_id}:delivered`. TTL defaults to the SAS URL's lifetime, so a retry past that window correctly re-uploads (the old URL is dead anyway).
- `downloader_bot/download/ratelimit.py` — Per-guild token bucket for `/download` enqueues, keyed `ratelimit:guild:{guild_id}`. `acquire(redis, guild_id, *, capacity, refill_per_hour)` returns `(allowed, retry_after_seconds)`; atomicity comes from Redis `WATCH`/`MULTI`/`EXEC` with optimistic retry on `WatchError` (no Lua, so `fakeredis` covers it in tests without the `lupa` binary dep). Capacity/rate are read from `settings.GUILD_RATE_LIMIT_BURST` (default 2) and `settings.GUILD_RATE_LIMIT_PER_HOUR` (default 5). TTL is `2x` worst-case full-refill time (min 1h) — a bucket idle long enough to refill can be evicted safely. Invoked from `cogs/download.py` with an explicit guild-owner bypass.
- `downloader_bot/download/discord_rest.py` — `open_client(token)` / `close_client(client)`. The worker uses `discord.Client(intents=Intents.none())` and only ever calls `login()` (no gateway, no `connect()`), which gives the REST surface (`fetch_*`, `channel.history()`, etc.) without paying for a gateway connection.

### Database (`downloader_bot/db/`)

Single-table Postgres schema bootstrapped via `CREATE TABLE IF NOT EXISTS` + an idempotent `ALTER ... DROP CONSTRAINT IF EXISTS / ADD CONSTRAINT` in `build_pool()` — alembic deferred until there's more than one table.

- `downloader_bot/db/schema.sql` — `guild_settings(guild_id BIGINT PK, delivery_mode TEXT CHECK IN ('dm','channel') DEFAULT 'dm', results_channel_id BIGINT, allowed_media_types TEXT[], max_archive_size_bytes BIGINT, retention_hours INT DEFAULT 24, created_at TIMESTAMPTZ, updated_at TIMESTAMPTZ)` plus a `guild_settings_channel_requires_id` CHECK (`delivery_mode <> 'channel' OR results_channel_id IS NOT NULL`) so the invariant is enforced in the DB, not the app layer.
- `downloader_bot/db/pool.py` — `build_pool()` (opens the asyncpg pool **and** applies `schema.sql`) and `close_pool(pool)`. Called from the Taskiq worker's startup hook in `downloader_bot/tq.py`.
- `downloader_bot/db/guild_settings.py` — `GuildSettings` frozen dataclass + `GuildSettingsRepo` (a thin async repo with `.get(guild_id) -> GuildSettings` and `.upsert(settings)`). `GuildSettings(guild_id=N)` constructed without a DB row yields safe defaults (`delivery_mode='dm'`, no channel, no media-type filter, 24h retention).

### Error handling pattern

Cogs raise **typed exceptions**; the global `on_command_error` handler in `downloader_bot/bot.py` translates them into user-facing embeds via the helpers in `downloader_bot/embeds.py` (`success`, `error`, `info`). Don't write per-cog error embeds for storage failures — raise from `downloader_bot/storage/exceptions.py` (`StorageConfigError`, `UploadError`, `SignedUrlError`) and let the central handler format the message. discord.py's built-in errors (`CommandOnCooldown`, `MissingPermissions`, `BadArgument`, etc.) are also handled centrally. Cog-local `cog_command_error` is fine for cog-specific custom checks (see `downloader_bot/cogs/setup.py`'s `NotGuildOwner` handling).

On the worker side, anticipated errors live inside the task body — `UploadError` and `SignedUrlError` triggering the partial-blob cleanup in the `try/finally`, `discord.Forbidden` / `discord.NotFound` from `fetch_channel` / DM / channel post, `AttachmentStreamError` from a mid-flight HTTP failure. Anything unexpected propagates out of the task; Taskiq's `SimpleRetryMiddleware` retries it (up to 3 times) with the same `task_id`, and the idempotency layer makes that safe.

### Storage layer (`downloader_bot/storage/`)

- `downloader_bot/storage/base.py` — `StorageBackend` ABC. Implementations expose `upload_and_sign(name, data: bytes | IO[bytes] | AsyncIterable[bytes], *, ttl, overwrite, content_type, download_filename) -> str` and `delete_blob(name) -> None`, plus async-CM dunders. The `AsyncIterable[bytes]` arm is what the streaming pipeline uses. `download_filename` decouples the **storage key** (a safe, collision-free `channel-{id}-{task_id}.zip`) from the **user-facing filename** (the friendly `channel-general-2026-05-09.zip`) by adding a Content-Disposition response override into the SAS — so downloads land on disk with the human-friendly name without changing the blob's primary key. `delete_blob` is best-effort cleanup: a missing blob is success; other backend errors re-raise as `UploadError` so callers can swallow them without importing the SDK. The worker imports the ABC, never a concrete provider module.
- `downloader_bot/storage/__init__.py` — `get_storage_backend()` is the dispatcher. It reads `settings.STORAGE_BACKEND` and lazily imports the matching provider module so deployments without that provider's SDK installed never fail to import the package.
- `downloader_bot/storage/azure.py` — `AzureBlobBackend` is the only concrete implementation today. Wraps `azure.storage.blob.aio.ContainerClient`; constructor takes an optional `client=` for dependency-injected mocks. Reads `settings.AZURE_CONN_STR` / `AZURE_CONTAINER`. SAS generation requires the connection string to carry an `AccountKey` — SAS-token-only or MSI credentials raise `SignedUrlError` at first call, not at startup. `_format_content_disposition(filename)` handles the RFC 5987 dance for non-ASCII filenames (emits both `filename="..."` ASCII fallback and `filename*=UTF-8''...`). `delete_blob` swallows `ResourceNotFoundError` (a missing blob is success); other `AzureError`s are caught and re-raised as `UploadError` / `SignedUrlError`. The Azurite-only SAS host rewrite (`AZURE_INT_URL` → `AZURE_EXT_URL`) lives at the bottom of `upload_and_sign` and is gated on `settings.ENVIRONMENT == "dev"`.

### Worker liveness (`downloader_bot/worker/healthcheck.py`)

Replaces the previous ARQ `arq --check` healthcheck. `HeartbeatMiddleware` writes a per-PID Redis key `taskiq:heartbeat:{role}:{pid}` with a 90s TTL on every `pre_execute` / `post_execute` boundary and on a 30s idle-refresh loop — so an idle worker still looks alive to the compose healthcheck. The CLI probe (`python -m downloader_bot.worker.healthcheck`, wired into both the worker and scheduler compose services' `HEALTHCHECK`) exits 0 iff at least one fresh sentinel exists for the role read from `TASKIQ_PROCESS_ROLE` (`worker` or `scheduler`).

### Config (`downloader_bot/config.py`)

pydantic-settings `Settings` model loaded from `.env`. Import the singleton: `from downloader_bot.config import settings`. Never re-read env vars with `os.getenv` — go through `settings`. `ALLOWED_MEDIA_TYPES` is parsed as JSON automatically by pydantic. Keys you'll touch most often: `TOKEN`, `PREFIX`, `ENVIRONMENT`, `POSTGRES_DSN`, `REDIS_URL`, `RABBITMQ_DEFAULT_USER` / `RABBITMQ_DEFAULT_PASS`, `AZURE_CONN_STR`, `AZURE_CONTAINER`, `AZURE_INT_URL` / `AZURE_EXT_URL` (dev-only SAS rewrite), `ATTACHMENT_CHUNK_SIZE` (CDN read chunk size for the streaming-zip pipeline; default 64 KB — also the upper bound on per-job in-flight bytes from the CDN), and the optional `TASKIQ_ADMIN_*` set that points the admin middleware at the `taskiq_admin` UI. The README env-var table is the canonical reference.

## Conventions worth knowing

- **Adding a top-level Python file or directory**: drop it under `downloader_bot/`. The prod `Dockerfile` ships the entire package via `COPY /downloader_bot /bot/downloader_bot`; the dev image's `CMD` (bot) and the worker/scheduler compose `command:`s (Taskiq with `--reload-dir /bot`) all watch the same directory. No Docker / compose changes are required for new files.
- **Tasks need to be importable by the worker.** The worker is launched as `python -m taskiq worker downloader_bot.tq:broker downloader_bot.tasks` — the trailing module path is what Taskiq imports to register tasks. New task modules either go inside `downloader_bot/tasks/` (re-exported through `downloader_bot/tasks/__init__.py`) or get an explicit `-tp` flag added to the compose command. Auto-discovery via `-fsd` is brittle in this codebase (see the recent fix in `735191d`); prefer explicit imports.
- **Imports are absolute and package-qualified.** Use `from downloader_bot.config import settings`, `from downloader_bot.tq import broker`, etc. The bot is run as `python -m downloader_bot.bot` and the worker/scheduler as `python -m taskiq ... downloader_bot.tq:broker`, all with `WORKDIR=/bot` so the package resolves on `sys.path`.
- **Every directory under `downloader_bot/` is a regular package** with an `__init__.py` (usually empty). Don't add namespace-package tricks — keep these as plain packages so static analysers and IDE tooling resolve them cleanly.
- **Task payloads must be JSON-serialisable.** Taskiq's aio-pika broker serializes via JSON by default; keep payloads JSON-friendly (ISO timestamps as strings, lists not sets) so they're inspectable in RabbitMQ and survive worker version skew. The `download_channel_media` task signature deliberately accepts primitive `int`s rather than richer types.
- **Don't reach into `ctx.state` directly in new tasks.** Use the typed providers in `downloader_bot/tq.py` (`get_storage`, `get_redis`, etc.) via `Annotated[T, TaskiqDepends(provider)]`. New shared worker resources should land as a startup-hook attribute on `state` **and** a provider function alongside it.
- **Schema changes** today mean editing `downloader_bot/db/schema.sql` and shipping; it re-runs idempotently on worker pool startup. If a migration ever needs to drop a column or backfill, that's the point at which alembic earns its keep — don't add it preemptively.
- **All I/O is async.** Don't introduce synchronous storage-SDK or `requests` calls; use the SDK's async client (`azure.storage.blob.aio` for the Azure backend) and `aiohttp` everywhere else.
- **Stream end-to-end.** The download pipeline (HTTP chunks → `stream-zip` async generator → Azure block-blob upload) keeps memory bounded regardless of channel size. Never materialise the full archive in a `BytesIO`; never introduce a scratch directory. The streaming invariant is enforced by `tests/download/test_zip_stream.py`.
- **Storage key vs display name.** Don't reuse the Discord-display filename as the blob key — keys must be stable for retries and free of user-controlled characters. Pass the friendly name as `download_filename=...` to `upload_and_sign` and the backend will encode it into the SAS as a Content-Disposition override. The key itself stays `channel-{channel_id}-{task_id}.zip`.
- **Hybrid commands** (`@commands.hybrid_command` / `@commands.hybrid_group`) need an owner to run `<PREFIX>sync global` (or `guild` for instant local testing) before the slash UI reflects changes.
- **`dm_me` flag on `/download`** propagates from the cog into the Taskiq task and forces `effective_delivery_mode='dm'` inside the task body. The cog's initial `context.defer(ephemeral=dm_me)` and ack `context.send(..., ephemeral=dm_me)` already respect it.
- **Per-invocation filters on `/download`** (`media_type`, `from_user`, `before`, `after`, `during`) ride alongside `dm_me` as a single `DownloadFilters` dict in the Taskiq payload. The cog validates and the task calls `filters_module.resolve(...)` to build the matcher; the matcher's category check is **intersected** with the guild's `allowed_media_types`, so user-supplied filters can narrow but never bypass admin policy. If you add a new filter, extend `DownloadFilters` + `resolve` together — never branch on filter shape inside the cog or task body.
- **Idempotent delivery** is enforced by the Redis keys in `downloader_bot/download/idempotency.py` (`task:{task_id}:archive_url` and `task:{task_id}:delivered`). Taskiq retries preserve `task_id`, so retried attempts skip phases that already completed. If you add a new delivery path, route it through the same idempotency check rather than calling `user.send` / `channel.send` directly.
- **Per-guild rate limit on enqueue.** `/download` consumes one token from a Redis-backed per-guild bucket (`downloader_bot/download/ratelimit.py`) at cog time, before `.kiq(...)` — counting enqueues, not completions, so a flooded queue is the failure mode being prevented. Guild owners bypass; DM-context invocations are exempt (no guild to limit). When adding another command that enqueues a long-running Taskiq job, decide explicitly whether it should share this bucket, get its own (`ratelimit:<scope>:<id>`), or skip rate-limiting altogether — don't accidentally leave a bypass.

Don't repeat parameter types inside `Args:` — the signature's type annotation is canonical (write `name: Description.`, not `name (str): Description.`).
